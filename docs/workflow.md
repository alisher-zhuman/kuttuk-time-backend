# KuttukTime - как работаем (ведущий по проекту)

Читать перед любой задачей. Детали архитектуры, API и решений - в `CLAUDE.md`; здесь - роль, правила работы, окружение и текущее состояние.

## Роль

- Правишь только этот репо (backend). `../frontend` читаешь, но **не меняешь**: для фронта пишешь промпт, пользователь передаёт его фронт-агенту. Каждый такой промпт подписывай «**Фронту:**».
- Работаем пошагово: один шаг за раз.
- Сначала проверь в коде/доках, потом утверждай. Неизвестное - «не знаю / не могу подтвердить», не угадывай.
- Ищи слабые места в решениях пользователя и говори прямо. При нескольких вариантах - сравнение и чёткая рекомендация.

## Как общаться с пользователем

- По-русски. Прямо, без воды и лишнего энтузиазма, максимум сути.
- Не объяснять базу без запроса.
- Любую цифру - с расчётом или источником.
- Факты отдельно от мнений.
- Не хватает контекста - сначала спросить, не угадывать.
- Длинные ответы - короткими блоками и списками.

## Бэк и фронт - кто за что (решение пользователя 2026-11-04, уточнено 2026-11-10)

- **Бэк-агент (я) - ведущий и архитектор:** продуктовые решения, контракт API, общие правила проекта (тон текстов, пуш и деплой, процесс), план задач. Источник правды - `CLAUDE.md` бэка и этот файл.
- **Фронт-агент** делает задачи фронта по промтам «Фронту:» и следует своим фронтовым правилам (`../frontend/CLAUDE.md`).
- **Строгое разделение** (пользователь 2026-11-10): я **никогда** не лезу во фронт - не правлю, не читаю его код и скриншоты, не проверяю его работу сам (уточнено 2026-11-10: «почему ты к нему полез»); только даю промт с контрактом и работаю по отчёту фронта, неясное - спрашиваю следующим промтом. Фронт никогда не делает задачи бэка. Даже мелочь во фронте - через промт.
- **Полная синхронизация:** любое общее правило или решение (тон, тире, пуш, продуктовые решения) - записываю у себя и **в том же ответе** даю фронту промт записать его в его `CLAUDE.md`. Расхождение между документами - правда здесь, фронту - промт поправить.

## Прод

- **Чтение** из прод-БД (`psql` SELECT, `npm run report:payouts`) - можно самому.
- **Любая запись** в прод (`npm run orders:resolve-review`, ручной UPDATE/INSERT, миграции вне деплоя) - только после явного «да» пользователя в чате.
- **Деплой (с 2026-10-22): Koyeb берёт ветку `dev`**, как Vercel на фронте. **Пуш в `dev` = деплой на прод.** PR в `main` не открываем; `main` больше не используется и отстаёт - так и оставляем (как на фронте).
- **Пушим пачками** (решение пользователя 2026-10-22): каждый пуш = пересборка и перезапуск прода. Коммитим после каждого проверенного шага **локально**; пушим, когда готова задача или пачка задач; правки только в документации отдельно не пушим - уходят со следующим пушем кода. Исключение - срочный фикс прода: пушим сразу. Перед пушем - сказать пользователю, что уходит.
- **Перед каждым пушем** (Koyeb не ждёт CI - красный коммит всё равно задеплоится):
  1. `npm run typecheck` и `npm run lint:check`;
  2. `npm test` и `npm run test:int` (нужен запущенный Docker);
  3. в коммите с миграцией - **сначала бэкап прода**: `docker run --rm --env-file <(grep -E '^PG' ~/.kuttuk/prod-db.env | tr -d "'\"") -v ~/.kuttuk/backups:/out postgres:18 pg_dump -Fc -f /out/prod-<дата>-<что>.dump` (локальный `pg_dump` 14 не подходит к Postgres 18), проверить, что файл есть.
- **После пуша:** дождаться деплоя и проверить на проде то, что меняли (`curl` к адресу; при миграции - таблица `migrations`). Если в панели Koyeb спрашивает - **Trigger build**, не «Skip build».
- Секреты прода: `~/.kuttuk/prod.env`, `~/.kuttuk/prod-db.env`, beta Finik - `~/.kuttuk/finik-beta.env` (chmod 600, вне репо); бэкапы - `~/.kuttuk/backups/`.
- Фронт деплоится на Vercel из `dev` (осознанно): пуш фронта в `dev` = прод.
- Koyeb Hobby засыпает без трафика: холодный старт, крон тикает только когда инстанс проснулся, Finik может ретраить webhook.

Для скриптов с прод-окружением, например `bot:setup`: `( set -a; . ~/.kuttuk/prod.env; set +a; npm run bot:setup -- --dry-run )`. Значения не выводить. Если пользователь сменит секреты на Koyeb - обновить и этот файл.
- Доступ к прод-БД: `~/.kuttuk/prod-db.env` (`chmod 600`, только `PG*`: host/port/user/password/database/sslmode). Подключать на время команды и только на чтение, значения не выводить:
  ```bash
  ( set -a; . ~/.kuttuk/prod-db.env; set +a; export PGOPTIONS='-c default_transaction_read_only=on'
    /opt/homebrew/opt/libpq/bin/psql -X -P pager=off -Atc "select …" )
  ```
  Для `pg_dump` - то же окружение. Для скриптов (`report:payouts`, `orders:resolve-review`) - `DATABASE_*` из того же файла: `DATABASE_HOST=$PGHOST` и т.д. Прод-env целиком (Finik, Cloudinary, бот) локально **не хранится** - не нужен.
- Прод-Postgres 18 → использовать `/opt/homebrew/opt/libpq/bin/pg_dump` и `/opt/homebrew/opt/libpq/bin/psql` (системный `pg_dump` 14 не подходит). `psql` запускать с `-P pager=off`, иначе вывод пропадает.

## Finik - выученное в бою

- Подпись webhook проверяется нашим `node:crypto` signer; host/path берутся из `FINIK_WEBHOOK_URL`.
- Finik приклеивает к `RedirectUrl` `?paymentId=…&status=succeeded` через `?`, не глядя на уже существующий query. Поэтому `RedirectUrl` ведёт на наш `/api/payments/return/:orderId` (подтверждено логами).
- Webhook приходит только на успех; бывает повтор - идемпотентность обязательна. Повтор переподписан (новый `x-api-timestamp`). Разбор единственного повтора (17.10, через 28 с) - не холодный старт: приложение не спало, ответ быстрый; причина на стороне Finik неизвестна и не важна, пока повтор безвреден. **Закрыто, не копать.**
- Тест-вектор подписи в их документации битый.
- Минимальная сумма платежа ≤ 1 сом (проверено).
- Кабинет: `finik.kg/admin`. Счёт для зачислений - корпоративный «ИП Алишер Жуманов» (его accountId - в `FINIK_ACCOUNT_ID`). Не путать с личным счётом и с «ID пользователя».
- Prod-путь создания платежа - `/v1/payment` (в кабинете написано `/payment` - неверно, smoke подтвердил `/v1`).
- Есть контакт с сотрудниками Finik в Telegram - вопросы можно задавать через пользователя.
- Открытые вопросы к Finik:
  - beta-доступ (запрошен письмом на finik@quickpay.kg 12.10, ответа нет);
  - сплит-платежи / схема для маркетплейса;
  - есть ли API статуса платежа и API возвратов;

## Решения по продукту (кратко; детали - в `CLAUDE.md` → Product decisions)

- Роли только `user` / `merchant` / `admin`; гасит владелец мерчанта; погашение только целиком; выплата за продажу, 90/10, неделя пн-вс по Бишкеку.
- **merchant ≠ venue** (2026-10-20): merchant - бизнес-аккаунт владельца (Telegram, роль, кабинет, отключение, выплаты), venue - заведение на витрине. У мерчанта может быть несколько заведений. Выплата - по `orders.merchantId` (владелец на момент продажи); гасит текущий владелец заведения; кабинет - по всему мерчанту + `?venueId=`. Детали - `CLAUDE.md` → Product decisions.
- Схемы фронта - без необоснованных nullable; фронт не хранит свои списки значений, берёт их с бэка.
- Терминология UI:
  - «Мерчант» - только в en; в ru - «заведение» / «Кабинет», в kg - «мекеме» / «Кабинет».
  - Срок действия в kg - «жарактуу» (не «колдонулат», чтобы не путать с «колдонулду» = использован).
  - «Не удалось загрузить» в kg - «жүктөө мүмкүн болгон жок».
- Остаёмся мини-аппом. В будущем - отказ от Finik в пользу прямых интеграций с банками (OTP).
