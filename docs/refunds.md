# Возвраты — как правильно делать (черновик 2026-10-22)

**Статус:** не реализовано. Решение пользователя: «когда будет такой кейс — вернёмся». Здесь описано, что делать
вручную, пока кейсов мало, и что строить, когда их станет больше. Юридические требования (Закон КР «О защите прав
потребителей», публичная оферта) **не проверены** — перед запуском показать этот документ юристу.

## Из чего исходим

- Сертификат — это **предоплата** услуги заведения. Деньги покупателя приходят на ИП через Finik, мерчанту раз в
  неделю уходит 90% **за продажу** (не за погашение).
- Сертификат может быть уже **выплачен мерчанту** (`orders.payoutId` заполнен) или ещё нет. От этого зависит, у кого
  деньги и откуда их вернуть.
- API возвратов у Finik **нет** (на 2026-10-12). Деньги покупателю возвращаем вне системы (банковский перевод),
  а в системе только **фиксируем** возврат — как сейчас `--refunded` для `needs_review`. Спросить Finik, умеют ли
  они возврат по транзакции: тогда деньги вернутся тем же способом, без реквизитов покупателя.
- Покупатель для нас — Telegram-аккаунт. Связь — бот (если он разрешил сообщения) или поддержка `@alisher_zh`.
- Код у того, кому подарили, — **владелец сертификата в системе остаётся покупатель**. Возврат — только покупателю
  (тому, кто платил), и только по неиспользованному сертификату.

## Правила по случаям (рекомендация)

| Случай | Возвращать? | Откуда деньги |
|---|---|---|
| 1. Передумал, сертификат **активен и не использован** | **Да, в течение 14 дней** с покупки, полностью | Не выплачено → просто не выплачиваем; выплачено → вычитаем из следующей выплаты мерчанту |
| 2. Сертификат **истёк, не использован** | **Нет** (деньги остаются у мерчанта). Жест доброй воли — продлить срок вручную, если мерчант согласен | — |
| 3. **Заведение закрылось** или перестало принимать сертификаты | **Да**, всем активным сертификатам, полностью | С мерчанта: вычет из невыплаченного; не хватило — долг мерчанта по договору, а до его возврата — убыток платформы |
| 4. Заведение **отказалось обслужить** по действующему сертификату | **Да**, после проверки (спросить мерчанта) | С мерчанта, как в п. 3 |
| 5. Проблемы с оплатой (сумма не совпала, двойное списание) | Да — уже есть: `needs_review` → `orders:resolve-review --refunded` | Мерчанту не выплачивалось |
| 6. Сертификат **погашен** (в т.ч. «это был не я», код украли) | **Нет** по умолчанию — код работает как наличные, об этом сказать в оферте. Разбор вручную, если мерчант признаёт ошибку | — |

Почему так:
- **14 дней на «передумал»** — привычный срок, покупателю спокойнее покупать; позже — сертификат мог уже лежать у
  друга как подарок, и вопросов «кто имеет право» больше.
- **Возврат целиком, комиссию Finik (~2%) берём на себя** — суммы маленькие, доверие дороже.
- **Истёкший не возвращаем** — так делает большинство сервисов сертификатов, мерчант уже получил деньги и держал
  услугу. Мы уже напоминаем за 7 дней до конца срока (бот). Это место — первое, что проверить у юриста.
- **Закрытие заведения — наша ответственность перед покупателем**, даже если мерчант не отдал деньги: покупатель
  платил нам.

## Что прописать в документах (до запуска)

- **Оферта для покупателя:** сертификат — предоплата; срок действия; код = право на услугу, передача кода = передача
  сертификата; возврат неиспользованного в течение 14 дней; истёкший не возвращается; при закрытии заведения — возврат.
- **Договор с мерчантом:** мерчант обязан обслуживать действующие сертификаты до конца срока; при закрытии или
  отказе — возврат стоимости активных сертификатов (вычетом из выплат или переводом); предупредить нас о закрытии
  заранее (например, за 30 дней), чтобы мы успели предупредить покупателей.

## Сейчас, вручную (пока кейсов единицы)

1. Покупатель пишет в поддержку → найти заказ: админка «Заказы» (поиск по коду или id заказа).
2. Проверить: сертификат `active` и не использован, кто платил (`buyer.telegramId`), выплачен ли заказ мерчанту
   (`payoutId`).
3. Вернуть деньги переводом (или через Finik, если появится возврат по транзакции).
4. Зафиксировать **SQL с «да» пользователя** (скрипта пока нет — сделать его первым же кейсом, по образцу
   `orders:resolve-review`): заказ → `refunded`, сертификат → `expired` (нового статуса пока нет), записка в
   `order_resolutions` (что, кому, когда, как вернули).
5. Если заказ ещё не выплачен — при статусе `refunded` он сам выпадет из отчёта выплат (там только `paid`).
   Если уже выплачен — CHECK `orders_payout_only_paid` не даст поставить `refunded` при заполненном `payoutId`:
   это и есть случай «вычесть из следующей выплаты», его вручную пока не делаем без скрипта.

## Что строить, когда кейсов станет больше

- **Статус сертификата `refunded`** (сейчас `active | used | expired`) — погасить такой нельзя; фронт показывает
  «Возвращён». Миграция enum + `effectiveStatusSql` + схемы фронта.
- **Таблица `refunds`**: `orderId`, `amount`, `reason` (`changed_mind` / `venue_closed` / `refused_service` / …),
  `method`, `note`, `refundedBy`, `createdAt`. Запись в одной транзакции со сменой статусов, как `order_resolutions`.
- **Вычет из выплаты:** если заказ уже выплачен — строка-корректировка против мерчанта (отрицательная сумма), которая
  уменьшает `due` следующей недели; итог недели не уходит ниже нуля — остаток переносится дальше. `payoutProgress()`
  и отчёт учитывают корректировки.
- **Скрипт / кнопка в админке** «Вернуть» с проверками (только `paid` + сертификат `active`; срок 14 дней — только
  предупреждение, решает админ) и сообщение покупателю в бот.
- **Закрытие заведения:** список активных сертификатов мерчанта + рассылка их владельцам в бот («заведение закрывается,
  напишите — вернём деньги» или «успейте до …»).
